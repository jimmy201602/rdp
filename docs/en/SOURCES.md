# Sources, Provenance, and Implementation Boundaries

## Sources for This Round

The new modules in this round were written from the public protocol specifications; no code, tests, or state machines were copied from the parent project, PyRDP, Redemption, or grdp. Only the Go standard library is used; there are currently no third-party Go module dependencies.

Pointer rendering (`bitmap` package): XOR mask (1/8/15/16/24/32bpp, bottom-up, row stride taken from lengthXorMask/height) and AND mask (1bpp, MSB first) composited into an RGBA cursor — AND=1 with black XOR → transparent, AND=1 otherwise (screen inversion) → approximated as opaque black, 32bpp with any non-zero alpha is alpha-premultiplied and the AND mask ignored; the number of cache slots is the client-declared colorPointerCacheSize (20) in the Pointer Capability Set 2.2.7.1.5 — out-of-range cacheIndex values are displayed but not cached, Cached misses are counted as errors; Null hides the cursor, Default restores the system cursor (this implementation does not draw a system cursor). Bitmap Update decoding (`bitmap` package): TS_CD_HEADER 2.2.9.1.1.3.1.2.3, RLE_BITMAP_STREAM 2.2.9.1.1.3.1.2.4, and Interleaved RLE decompression 3.1.9 (all regular / lite / MEGA_MEGA / special orders, first-line vs. non-first-line XOR semantics, foreground pixel insertion between BG_RUNs; the initial foreground color for 15bpp is 0xFFFF per the reference implementation); bitmaps are bottom-up and clipped to destLeft..destBottom (inclusive) and the desktop bounds when drawn; pixel formats: 8bpp via Palette Update (2.2.9.1.1.3.1.1), RGB555 / RGB565 / BGR24 / BGRX32 to RGBA. Not implemented: MS-RDPEGDI orders and bitmap cache, Surface Commands, RDPGFX and its codecs, fast-path input.
- The MS-RDPBCGR/MS-RDPELE entries above are cited by section number; the entry points are https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpbcgr/ and https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpele/ respectively; per-section permalinks will be added when archiving before release.
- The two non-spec details observed during xrdp interop (the built-in proprietary certificate's 512-bit declaration vs. 511-bit modulus; the zero-length blob's `wBlobType`=0x1428 in STATUS_VALID_CLIENT) came from runtime observation, not from reading xrdp source code; the handling in both cases is grounded in public specification text (see docs/VALIDATION.md 5.3).

The specification versions and legal applicability clauses still require a formal archival review before release.

## Claims That Must Not Be Made

This session had prior exposure to the old project's source code, so this development must not be claimed as a strict clean-room proof. Independent authorship, passing tests, or the absence of GPL strings do not amount to a completed provenance audit. `LICENSE` only states the intended proprietary distribution boundary for the new original parts in this directory; it does not change the licensing of the parent project or any third party.

## Test Materials

Unit tests use data constructed according to the specifications and test certificates generated at runtime; no old-project test source or real credentials are copied. xrdp serves only as a standalone interop test server in a VM; it is not linked into or copied into the kernel and is not a runtime dependency of the product. The test service is mapped only to the VM loopback and is not published to the public internet.

## Explicitly Not Implemented in This Round

NLA/CredSSP, Standard RDP Security encryption, the rest of graphics encoding/decoding (after Font Map, only Bitmap Update decoding into a framebuffer and pointer decoding into cursors: orders not parsed, Surface Commands only counted, no bitmap cache / RDPGFX / codecs, no fast-path input), input, static/dynamic virtual channel data, RemoteApp, recording/playback, business migration. The implemented parts stop at Font Map: `Probe` up to TLS (without negotiation-result reconfirmation), `Connect` up to Channel Join (with reconfirmation, no Client Info sent), `Activate` up to Font Map, and `Options.Observe` keeps reading server output within its window (Client Info is sent; INFO_AUTOLOGON is set only when the caller supplies a password; user authentication is handled by the server afterwards, and the result is visible only if the server sends Save Session Info / Set Error Info — xrdp 0.9.24 does not, see docs/VALIDATION.md 5.4). The licensing Platform Challenge / New License / Upgrade License branches are verified only against the local fake server and the public samples. None of the three justifies claiming that a secure, authenticated, complete RDP session has been established.

G3-1 adds the server role (`server` package, `cmd/rdpserve`): the server side of the MS-RDPBCGR 1.3.1.1 connection sequence, implemented up to Font Map and the subsequent Bitmap Update / Pointer push; the BER encoding of MCS Connect-Response was checked byte for byte against the public MS-RDPBCGR 4.1.4 sample (spec integer encoding `02 03 00 ff f8`), Connect-Initial / CS_* decoding against the 4.1.3 sample, and Demand Active encoding round-tripped against the 4.1.12 sample. Licensing sends only a STATUS_VALID_CLIENT error alert (2.2.1.12.1.3); no licenses are issued and no RDS license server is implemented; the server does not do NLA/CredSSP, Standard RDP Security, input handling, virtual channel data, orders, compressed bitmap encoding, fast-path output, Server Redirection, or Auto-Reconnect. Authorization policy is entirely up to the caller's callback; this package stores no credentials; upstream target proxying (the gateway) is G3-3 and is not implemented.
